# 方案:修复 execute 流程(worktree 安全 + 经理工具调用验证 + bd→git 关联)

## 三步,按依赖顺序

### 第一步:加"经理没干活"的响亮告警(P0,最紧急)

**问题**:这次 execute 经理进程退出了但没调用任何工具(split/assign/test 一个没跑),主进程却报"EXECUTE 完成",让你误以为跑完了。

**改动**(extensions/workflow.ts):
- `assign_dev` 工具注册时,给 DevPool 加一个 `tasksProcessed` 计数器(已处理 task 数)
- `split_prd_to_tasks` 工具加一个 `hasSplit` flag
- 经理进程退出后(`cmdExecute` 的 exitCode 检查处),检查:如果 `!hasSplit && tasksProcessed === 0` → notify 升级为 **error** 级别 + 明确文案"经理进程未调用任何工具,可能模型出错或 prompt 问题",而不是"EXECUTE 完成"
- 这样下次再发生"经理空跑",你会立刻看到红色警告,不会误以为成功

**注意**:devPool 是经理进程里的局部变量,主进程拿不到。但因为经理是 `--print` 模式 + stdio inherit,这个检查要在经理进程**内部**做(在 agent_end 或 session 结束 hook 里),或把结果写到 state.json 让主进程读。最小实现:在 workflow.ts 的 manager 分支注册一个 agent_end hook,检查 devPool 状态,如果 0 task 处理过就往 state.json 写个 `managerNoop: true`,主进程 cmdExecute 读它。

### 第二步:加固 dev-pool 的 worktree 安全(P1,防未来静默失败)

虽然这次没触发,但调研发现 dev-pool 有**危险的静默成功路径**。改动(extensions/dev-pool.ts + lib.ts):

1. **`runTask` 的 empty 判断**(dev-pool.ts:205-209):commitSubtask 返回 empty 时,**先验证 worktree 路径存在且 reasonix 真的跑过**。如果 worktree 为空但 reasonix 报告跑过,这是异常(代码写错地方了),应该 reopen 而不是"视为通过"。
2. **addWorktree 失败响亮报错**(lib.ts:174-180):bd worktree create 失败时,不要静默 fall through 到 git——至少 log stderr,让经理知道。
3. **runTask 开头加 worktree 存在性验证**:`fs.existsSync(dev.worktree.path)` 不存在时报错,不继续跑 reasonix。
4. **bare catch 改成有日志**(lib.ts:198, dev-pool.ts:253):worktree 清理失败至少留个痕迹。

### 第三步:bd→git 关联 + worktree 常驻(你要的改善)

**3a. bd issue 关联 commit sha**(dev-pool.ts runTask 的 bd close 处):
- commit 成功后,在 `bd close` 之前或之后,`bd comment <taskId> "代码提交: <sha> (<branch>)"`
- 这样 `bd show <id>` 能看到对应的 commit,bd 和 git 建立关联

**3b. worktree 按 dev 常驻,跨需求复用**(dev-pool.ts getOrCreate + cleanupAll):
- worktree 命名从 `wt-<reqId>-dev<N>` 改成 `wt-dev<N>`(跨需求复用)
- 分支从 `bd-<reqId>-dev<N>` 改成 `dev<N>`(常驻)
- `cleanupAll` 不再删 worktree,改成 `git reset --hard <主干>` 把 worktree 重置到最新主干,为下次准备
- 这样 3 个 dev 的 worktree + session 跨需求持久存在,省创建/删除开销,还能跨需求复用 session 上下文

## 实施顺序
1. 第一步(P0 告警)—— 最先做,立刻能防止"经理空跑被当成功"
2. 第二步(worktree 加固)—— 防未来静默失败
3. 第三步(bd→git 关联 + worktree 常驻)—— 你的架构改善

每步单独验证 + bd 跟踪。第一步最重要也最紧急。

## 不做的事
- ❌ 不改经理的 prompt/模型配置(经理为什么没调工具需要单独诊断,可能要加日志看 --print 模式的实际输出)
- ❌ 不改 /execute 的同步阻塞机制
- ❌ 不动 reasonix 本身
