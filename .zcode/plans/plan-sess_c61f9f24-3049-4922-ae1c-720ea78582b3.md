# 方案:回到 pi-agent + manager 主 session 化

## 核心思路

三个改变合在一起:
1. **底层从 omp 换到 pi-agent**(`@oh-my-pi/pi-coding-agent` → `@earendil-works/pi-coding-agent`)—— 摆脱 omp 绑定
2. **subagent 能力用 pi-subagents 插件**(社区插件,纯 pi 生态)—— 替代 omp 的 task 工具
3. **manager 从独立子进程变成主 session 自己**—— 不再 spawn manager 进程,主 session 直接跑流水线

第 3 点是最大的简化:删除 WF_ROLE 整套机制 + spawn manager 逻辑,主 session 用 `sendUserMessage` 触发流水线。这同时解决了"怎么看子任务执行情况"的痛点(交互式,全程可见可介入)。

## 架构图(重写后)

```
主 session(交互式,加载 workflow extension + pi-subagents 插件)
  │
  ├─ PRD 模式(wf.mode === "plan",lockReadonly 锁只读工具)
  │    你和 pi 讨论需求 → /wf prd 生成 prd.md
  │
  └─ build 模式(wf.mode === "build",/execute 触发)
       工具集:split_prd_to_tasks / bd_task / run_test / subagent / bash / read
       主 session 自己跑流水线(/execute 用 sendUserMessage 注入启动指令):
         ① split_prd_to_tasks(读 PRD → 拆 task → bd issue)
         ② 对每个 ready task:
              bd_task(claim) → subagent(dev) → subagent(reviewer) → bd_task(close/reopen)
         ③ 全部 close → run_test
       自动程度:默认一口气跑,异常(dev 反复失败/reviewer 多次 fail)停下问用户
       用户随时 /wf status 看进度,随时能插话(交互式)
```

## 实施步骤(分 5 步,每步可验证)

### 步骤 1:换底层 omp → pi + 装 pi-subagents(地基)

**1.1 package.json 依赖换回 pi**
- `@oh-my-pi/pi-coding-agent@^17.0.7` → `@earendil-works/pi-coding-agent@^0.81.0`
- 两处 import(workflow.ts:31, cache.ts:33):`@oh-my-pi/...` → `@earendil-works/...`

**1.2 getAllTools 破坏点修复(反向)**
- workflow.ts:161 的 `pi.getAllTools()` —— omp 返回 `string[]`,pi 返回 `ToolInfo[]`(有 .name)
- 改回:`pi.getAllTools().map((t) => t.name)`(从 omp 的简写恢复)

**1.3 安装 pi-subagents 插件**
- `pi install npm:pi-subagents`(用户操作,setup.sh 里加)
- 确认 `subagent` 工具出现在 pi 的工具集里

**1.4 二进制 omp → pi**
- workflow.ts 的 `resolveOmpBin()` → `resolvePiBin()`(改名 + which pi)
- setup.sh:omp 安装 → pi 安装

**验证**:`tsc` 通过 + `pi -e extensions/workflow.ts --print "OK"` 能起进程 + `subagent` 工具可用

### 步骤 2:agent 定义迁移(.omp/agents → .pi/agents + frontmatter 适配)

**2.1 目录迁移**
- `.omp/agents/` → `.pi/agents/`(pi-subagents 的发现路径)
- dev.md / reviewer.md / manager.md 移过去

**2.2 dev.md frontmatter 适配 pi-subagents 格式**
- omp 格式:`outputSchema: { JSON schema }`(结构化校验)
- pi-subagents 格式:`output: <文件路径>`(结果写文件)
- 改动:dev 把结构化结果(JSON)写到一个文件(如 `.workflow/<reqId>/results/<taskId>.json`),`output:` 指向它
- manager 用 read 读这个 JSON 文件拿到 {filesChanged, verifyPassed, commitSha, summary}
- frontmatter 加 `systemPromptMode: replace`(完整替换 system prompt,不继承主 session 的)

**2.3 reviewer.md frontmatter 适配**
- 同样的 output 机制 + `tools: read, grep, bash`(只读)

**2.4 manager.md 不再是 agent 定义**
- manager 就是主 session,不需要独立的 agent 定义文件
- manager.md 的内容(工作流程/动态粒度/约束)改成主 session 的 system prompt 注入(通过 before_agent_start hook 在 build 模式时注入)

**验证**:`pi` 启动时 discoverAgents 能发现 dev/reviewer

### 步骤 3:删 WF_ROLE 机制 + manager 工具始终注册

**3.1 删除 WF_ROLE 相关**
- workflow.ts: 删 `const WF_ROLE = ...`(line 95)
- 删 `registerManagerTools` 的 `if (WF_ROLE !== "manager") return`(line 670)
- 删 session_start 里的 `if (WF_ROLE === "manager")` 分支(line 855,state.json 恢复逻辑)
- 删 agent_end 里的 manager noop 检测(line 900)
- 删文件头 WF_ROLE 注释(line 22)

**3.2 manager 工具始终注册**
- `registerManagerTools(pi, ctx)` 在 session_start 里无条件调用(不再门控 WF_ROLE)
- 工具集切换靠 mode(不是 WF_ROLE):
  - plan 模式:lockReadonly(只读)
  - build 模式:setActiveTools([split_prd_to_tasks, bd_task, run_test, subagent, bash, read...])

**3.3 setActiveTools 白名单**
- 删 `task`(omp 的),加 `subagent`(pi-subagents 的)
- build 模式:`[split_prd_to_tasks, bd_task, run_test, subagent, ...READONLY_TOOLS, bash]`

**验证**:`pi` 启动后主 session 有 split/bd_task/run_test/subagent 工具

### 步骤 4:cmdExecute 从 spawn 进程改成主 session 触发

**4.1 删除 spawn manager 逻辑**
- 删 cmdExecute 的:resolve omp bin + spawn mgrProc + exit code 处理 + managerNoop 检测 + WF_ROLE env(line 560-630 大部分)

**4.2 改成 mode 切换 + sendUserMessage 触发**
- cmdExecute 新逻辑:
  1. PRD 解析 + epic 创建 + dirty check + baseline(保留)
  2. `wf.mode = "build"` + setActiveTools 解锁执行工具集
  3. `pi.sendUserMessage(managerPrompt)` 注入启动指令:
     "你是经理。需求 X,PRD 在 Y。现在按 manager.md 流程跑:先 split_prd_to_tasks,然后每个 task 走 claim → subagent(dev) → subagent(reviewer) → close/reopen。异常才停下问用户。"
  4. 主 session LLM 收到这条消息后开始跑(不再 await 子进程退出)
  5. cmdExecute 直接返回(主 session 异步跑流水线,用户可交互)

**4.3 manager.md 内容注入**
- loadManagerPrompt 简化:不再剥离 frontmatter + 注入运行上下文(因为没有独立进程了)
- 改用 before_agent_start hook:build 模式时把 manager.md 的工作流程注入 system prompt

**验证**:`/execute` 后主 session 开始拆 task + 派 dev,`/wf status` 能看到进度

### 步骤 5:端到端验证 + 文档/配置清理

**5.1 端到端测试**(像之前 calc-utils 那样)
- 建模拟项目 + bd init + PRD
- `/execute` 跑完整流水线
- 验证:dev 写代码 + commit、reviewer 审查、bd close、tsc 通过
- 关键验证点:subagent 工具在主 session 里能调通 + 结构化结果通过 output 文件传回

**5.2 配置清理**
- workflow.config.json:确认 providers/roles 不依赖 omp 特性
- setup.sh:omp → pi + pi-subagents 安装
- 删除 omp 残留引用

**5.3 文档**
- README.md / DECISION_LOG.md:记录"回到 pi + manager 主 session 化"的决策
- skills 四件套:omp subagent → pi subagent 措辞

## 风险与关键验证点

| 风险 | 等级 | 应对 |
|---|---|---|
| pi-subagents 的 subagent 工具在主 session + extension 混用下能否调通 | **高** | 步骤 1.3 后立即做 GO/NO-GO 测试(像之前 omp task 那样) |
| dev 结构化返回:output 文件机制能否可靠传回 manager | 中 | 步骤 5.1 端到端验证 |
| sendUserMessage 触发的主 session LLM 能否按 manager.md 流程自主跑完 | 中 | 步骤 5.1 端到端验证 |
| pi-coding-agent 和 omp 的扩展 API 其他差异 | 低 | 步骤 1 的 tsc + 加载验证会暴露 |
| 主 session 跑流水线时模型切换(discuss→split→dev 模型不同) | 中 | runStageText 已有切模型机制,但要确认 subagent 调用不干扰主 session 模型 |

## 不做(明确排除)
- 不用 pi-agents-team(定位不符:交互式个人编排,不支持 bd/验证门/PRD)
- 不引入 pi-loadout/pi-cache-graph 等辅助插件(第一版先跑通核心,辅助插件后续按需加)
- 不改 bd.ts / PRD 模式命令(cmdNew/cmdPrd/cmdAnalyze/cmdBug/cmdResume/cmdDone/cmdStatus)
- 不改 split_prd_to_tasks / bd_task / run_test 的工具逻辑(只改注册时机和工具名)

## 建议执行顺序
步骤 1(换底层 + GO/NO-GO)→ 步骤 2(agent 定义)→ 步骤 3(删 WF_ROLE)→ 步骤 4(cmdExecute 改主 session)→ 步骤 5(端到端验证 + 清理)

步骤 1 的 GO/NO-GO 是命门:如果 pi-subagents 在主 session + extension 下调不通,整个方案要调整。先验证再继续。
