# 迁移方案:抛弃 reasonix,改用 omp 原生 subagent

## 目标与原则

**目标**:去掉 reasonix 外部二进制依赖,dev 执行层改为 omp 原生 subagent;经理保留为常驻 LLM 管控者(动态粒度);支持最多 20 个 dev subagent 并发。

**核心原则**(本轮讨论已确认的全部决策):
1. dev subagent 只写代码 + **内部闭环验证**(写→验证→改 在 dev task 内完成)
2. 独立 task **并行**,但合并**串行**(避免 worktree 合并冲突)
3. 经理**保留为常驻 LLM**,动态粒度(默认阶段级放权,异常时细管)
4. 经理以 **omp detached subagent** 形态存在(同进程嵌套,经调研证实是一等公民)
5. **保留 assign_dev 工具 + DevPool 类**,内部把 `spawnReasonix` 换成 omp subagent 调用(DevPool 70% 逻辑复用)
6. 并发**目标 20**,分阶段实测(先 2-3 跑通,再逐步拉到 20)
7. **全面升级** `.omp/agents/*.md` 为正式 omp agent 定义
8. 类型包升级到 `@oh-my-pi/pi-coding-agent@^17.0.6`

---

## ⚠️ 必须先记录的关键修正(影响 cache 论证)

调研发现 **cache.ts 当前不覆盖 dev 层** —— 因为 dev 是独立 reasonix 进程。96% 命中率是 reasonix + `--continue` 的数字,**不是 cache.ts 的**。

**迁移后这个状况会改变**:dev 变成 omp 同进程 subagent 后,cache.ts 的 `before_agent_start` 钩子会对 dev 生效,前缀缓存从"只管 omp 讨论层"扩展到"也管 dev subagent 层"。

**但 dev subagent 的实际命中率未经实测**(其前缀更短更动态)。这是方案里**头号待验证项**,迁移后第一时间要测。

## 架构总图(迁移后)

```
主 session omp(用户交互, discuss 模型)
  │  /execute 触发
  ▼
task(manager subagent, deepseek-pro, detached)   ← 常驻 LLM 管控,动态粒度
  │  (manager.md 升级为正式 agent 定义)
  │
  ├─ 拆分阶段:自己读 PRD 拆(或调 split subagent)→ bd tasks + depends_on
  ├─ 分配阶段:对每个 task 调 assign_dev(task_id, dev_id)
  │     │  assign_dev 是 omp 工具,内部调 DevPool.runTask()
  │     ▼
  │   DevPool.runTask(devId, taskId):
  │     ① worktree 就绪检查 (复用)
  │     ② bd claim 原子认领 (复用)
  │     ③ spawn omp dev subagent (替代 spawnReasonix) ← 新
  │          spawn(omp, ["--print","--model","deepseek-flash",
  │                      "--system-prompt", <dev.md 内容>, instruction])
  │          dev 在 isolated worktree 写代码 + 内部闭环验证
  │     ④ 验证门 runVerify (复用,dev 内部已自验证,这是门禁确认)
  │     ⑤ commitSubtask (复用)
  │     ⑥ mergeWorktree 串行化 (复用 + 新增串行锁)
  │     ⑦ bd close/comment (复用)
  │     失败 → bd reopen + comment,经理决定重试/换 dev/细管
  ├─ 测试阶段:run_test(验证 + review subagent glm-5.2 + 建 bug)
  └─ 完成 → onJobComplete 自动交付主 session
```

**与现状的差异**:
- 经理:独立 omp 进程 → detached subagent(同进程嵌套)
- dev:spawn reasonix 二进制 → spawn omp 子进程(同 omp 二进制,不同 model/prompt)
- 调度:串行 + session 路由 → 并行 + bd 依赖图 + 串行 merge
- cache.ts:只管讨论层 → 覆盖全层(含 dev subagent)

### 阶段 1:DevPool 执行器替换(核心改动,改动最小)

**目标**:把 `spawnReasonix` 换成 omp subagent 调用,其余 DevPool 逻辑全部保留。

**1.1 新增 `spawnDevSubagent(instruction, cwd, dev): Promise<number>`**(替代 spawnReasonix,dev-pool.ts:265-277)
```
spawn(ompBin, [
  "--print",
  "--model", `${devModel.provider}/${devModel.model}`,   // deepseek-flash
  "--system-prompt", devRolePrompt,                       // 从 dev.md 加载(去 frontmatter)
  "--cwd", cwd,                                           // worktree 路径
  instruction,
], { cwd, stdio: ["ignore","pipe","pipe"], env })
```
- 返回 `Promise<number>`(退出码),与 spawnReasonix 契约一致
- `devRolePrompt` 从 `.omp/agents/dev.md` 加载(复用 loadManagerPrompt 的 frontmatter 剥离逻辑)
- timeout 改用 omp 的 wall-clock 或保留 SIGTERM 机制

**1.2 重构 `runTask` 的第 3 步**(dev-pool.ts:191-201)
- 删 `reasonixArgs(specPath, dev)`(dev-pool.ts:123-147)
- 改为组装 instruction(规格文件路径 + rolePrefix 内容移入 dev.md)
- 调 `spawnDevSubagent` 替代 `spawnReasonix`

**1.3 删除 reasonix 专属字段**
- `Dev.sessionStarted`(dev-pool.ts:43)及其 5 处引用(:114, :220, :142, :192, :260, :303)
- `reasonixArgs` 方法整体(dev-pool.ts:123-147)
- `spawnReasonix` 方法整体(dev-pool.ts:265-277)
- rolePrefix 文本块(dev-pool.ts:127-131)→ 内容迁移到 dev.md

**1.4 更新注释**
- dev-pool.ts:1-17 文件头(从 reasonix session 架构改为 omp subagent 架构)
- dev-pool.ts:279 死注释("Tear down all dev worktrees" 与 reset-only 实现矛盾)

**验证**:单个 task 走完整 runTask 流程(worktree→claim→dev subagent→验证→commit→merge→close)

### 阶段 2:agent 定义全面升级

**2.1 升级 `.omp/agents/dev.md` 为正式 omp agent 定义**
- frontmatter:`name: dev`, `description:`, `model: deepseek-flash`
- 新增(可选):`tools:` 白名单(限制 dev 只用 read/write/edit/bash/bd-work 等,不给 task 工具防越界嵌套)
- 正文:把原 rolePrefix 内容(dev-pool.ts:127-131)整合进来
- 删除 session 复用章节(dev.md:63-67)—— omp subagent 无 --continue
- 删除所有 "reasonix" 字样 → "omp subagent"
- **验证 dev 内部闭环验证**:在 dev.md 工作循环里明确"写完代码后自己跑验证命令,不过就改到过"

**2.2 升级 `.omp/agents/manager.md` 为正式 omp agent 定义**
- frontmatter:`name: manager`, `description:`, `model: deepseek-pro`
- 正文重写"动态粒度"管控策略:
  - 默认:阶段级决策(拆完→分配→测试→修 bug)
  - 异常细管触发条件:dev 反复失败、bug 修不好、task 异常困难
- 删除"dev 是 reasonix session"/"--continue 复用"相关描述(:11, :33, :77, :101)
- 更新分配策略:不再需要"依赖链给同一 dev"(改成按 bd 依赖图 + 并行)
- 更新 skill 白名单表里的 reasonix 引用

**2.3 (可选)新增 `.omp/agents/splitter.md` 和 `.omp/agents/reviewer.md`**
- 如果拆分/review 要做成独立 subagent(而非经理自己做),加这两个定义
- splitter: model deepseek-pro, 只读 PRD 输出 task 列表
- reviewer: model glm-5.2, 只读 diff 输出问题清单
- **决策点**:经理自己拆 vs 调 splitter subagent —— 建议第一版经理自己拆(改动小),后续再拆分

**验证**:omp 启动时 `discoverAgents` 能发现这些 agent 定义,经理能 `task(agent="dev")` 调用

### 阶段 3:并行与合并串行化

**目标**:从串行(assign_dev await)升级到 20 并发 + 串行 merge。

**3.1 DevPool 并发改造**
- `assign_dev` 工具改为支持并发:经理可以同时调多个 assign_dev
- DevPool 内部用 `mapWithConcurrencyLimit`(借鉴 omp parallel.d.ts 的模式)或自建信号量
- `execute.maxParallel` 配置项真正生效(现在是注释说"池大小非并发数")

**3.2 合并串行化(关键)**
- 新增 merge 锁:`async mergeSerial<T>(fn: () => Promise<T>): Promise<T>`
- runTask 第 6 步 mergeWorktree 包在锁里,确保一次只 merge 一个 dev 的分支
- 避免 20 个 dev 同时 merge 撞 `extensions/workflow.ts` 这类共享文件

**3.3 bd 并发**(调研确认安全,无需加锁)
- claim 原子已保证,close/comment 各自独立事务
- noms LOCK 自动序列化写,不会损坏
- **唯一注意**:高并发下 bd 写延迟,但不影响正确性

**3.4 并发配置**
- `workflow.config.json`:`execute.maxParallel` 从 3 调到目标值
- omp 设置:`task.maxConcurrency`(默认 32,够用)、`task.maxRecursionDepth: 3`(留余量)
- provider 并发:DeepSeek/gbgjxj 的 RPM/TPM 限制要实测(见阶段 5)

**验证**:3 个独立 task 并行跑通 → 逐步拉到 10 → 20

### 阶段 4:经理形态迁移(独立进程 → detached subagent)

**目标**:把 cmdExecute 的"spawn 经理 omp 进程"改为"主 session spawn 经理 detached subagent"。

**4.1 改造 cmdExecute**(workflow.ts:549-630)
- 当前:`spawn(omp, ["-e", extPath, "--print", "--model", managerModel, prompt])`
- 改为:主 session 通过 omp task 工具 spawn manager subagent
- 但注意:extension 层无法直接调 omp task 工具(那是 agent 对话内的工具)
- **实现路径**:主 session 收到 /execute 后,用 `pi.sendUserMessage` 注入一段 prompt,引导主 session agent 自己调 `task(agent="manager", detached=true, ...)`
- 或者:**保留 spawn 经理进程作为过渡**(第一版),验证 detached subagent 可靠后再切

**4.2 经理进程内的 task 工具可用性**
- 确认经理进程/经理 subagent 保留了 task 工具(taskDepth=1 < maxRecursionDepth)
- 经理能 `task(agent="dev", isolated=true)` 调 dev

**4.3 结果回报**
- detached subagent 完成 → onJobComplete 自动交付主 session
- 或用 hub 工具显式通信

**验证**:经理 detached subagent 能跑完整流水线,结果回报主 session

**⚠️ 这是最复杂的阶段,建议最后做,且可以先保留 spawn 经理进程形态跑通前面所有阶段后再切。**

### 阶段 5:实测与调优(20 并发验证)

**5.1 限流实测**(顺序拉高)
- 2 并发 → 5 → 10 → 20,每级观察:
  - DeepSeek API:429 限流?RPM/TPM 触顶?
  - gbgjxj relay:并发上限?
  - worktree:20 个的磁盘/内存占用
  - merge 串行排队延迟
  - cache.ts 命中率(dev subagent 层)

**5.2 根据实测调整**
- 限流:加 provider 并发限制 / 重试退避
- merge 延迟:优化串行策略(批量 merge?rebase?)
- 命中率:优化 dev 前缀稳定性(固定 skill 加载顺序等)

## 回退策略

每个阶段独立,失败可回退:
- 阶段 0 失败 → 不动 reasonix,维持现状
- 阶段 1 失败 → git revert dev-pool.ts,reasonix 路径仍在(spawnReasonix 只是改了,原逻辑可恢复)
- 阶段 2-4 失败 → agent 定义/经理形态可以独立回退,不影响 dev 执行层
- 阶段 5 实测不达标 → maxParallel 调回保守值,架构不变

**关键**:阶段 1 完成后,reasonix 已经可以卸载(dev 执行层换完)。阶段 2-4 是架构优化,不影响功能正确性。

## 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| cache.ts 对 dev subagent 命中率未实测 | **高** | 阶段 0.3 第一时间测,不达标则需优化 dev 前缀 |
| 20 并发触发 DeepSeek 限流 | 中 | 阶段 5 分级实测,加退避 |
| detached subagent 嵌套可靠性 | 中 | 阶段 4 可先保留 spawn 经理进程形态 |
| merge 串行成瓶颈 | 低 | 实测后优化(批量 merge / rebase) |
| omp 类型包其他兼容性 | 低 | 调研确认仅 1 处破坏(getAllTools) |
