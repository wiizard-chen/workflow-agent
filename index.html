一个 pi/omp coding-agent 扩展,把"需求 → PRD → 拆 task → 分配 dev → 测试" 做成 PRD / 执行 双模式流水线。
执行模式下,主 omp 启动一个技术经理(独立 session),它把 PRD 拆成 task、 分配给 omp dev subagent(omp --print,由 DevPool spawn)、最后让 glm-5.2 测试, 失败自动建 bd bug。

2两个模式的命令流

🟦 PRD 模式(讨论)

  1. /wf new <需求> [repo路径]
    bd init + 创建父 epic,进入只读模式
  2. 自由对话讨论需求
    deepseek-pro · plan-interrogation skill 自动追问
  3. /wf prd
    glm-5.2 生成 prd.md(缺简报先自动 analyze)
  4. 审阅 .workflow/<reqId>/prd.md
  5. 不满意 → 继续讨论后再 /wf prd

🟧 执行模式(/execute)

  1. /execute 启动经理 omp 进程(独立 session)
  2. 经理读 PRD → split_prd_to_tasks 拆 task 进 bd
  3. assign_dev(taskId, devId) 分配给 omp dev subagent
    DevPool spawn;独立 task 并行;dev 内部闭环 verify→fix
  4. run_test → glm-5.2 测试产出
  5. blocker 创建 bd bug → 经理再 assign_dev 修复
  6. 直到全过 → 经理退出,回主 session

4核心设计要点

🧠

调度 = LLM 判断,非代码循环

经理用三个工具(split/assign/test)自主决策拆分与分配顺序,不是硬编码的 while 循环。

♻️

跨 task 上下文(cache.ts + bd)

原 reasonix 的 --continue session 续跑已移除。跨 task 上下文改由 cache.ts 冻结 system-prompt date(前缀缓存跨 task 热)+ bd comments 显式携带状态。

🌳

并行派发策略

独立 task 并行散给不同 dev(取代旧的"依赖链给同一 dev 走 --continue"路由);dev 在 subagent 内闭环 verify→fix。

⚡

DeepSeek 前缀缓存

cache.ts 覆盖到 dev subagent 层:system-prompt date 冻结 → 前缀缓存跨 task/跨 dev/跨 worktree 保持热度(实测:cache_hit 2880 跨 worktree 共享)。

🗄️

bd 为权威状态层

子任务 DAG(依赖/状态/归属)存在 beads Dolt DB;.workflow/ 只放文本产物;代码改动走 git。

🛡️

编排与执行同源

经理 omp 管通用人工审阅与调度,dev omp subagent 跑实现 + 闭环验证,cache.ts 统一管 DeepSeek 前缀缓存——编排与执行同属 omp,无需外部二进制(原 reasonix 执行层已迁移为 omp subagent)。

6缺陷与改进(来自 KNOWN_ISSUES.md)

🔴 P0 — 安全假象

P0已修 ✓验证门 verifyCommand 默认空,形同虚设

原问题:没配 /wf verify,任何 omp dev subagent 改动都被判"验证通过",deepseek-flash 无监督写权限直接 commit。

改进:/build 现在严格验证——无验证命令默认失败,首次弹出确认让你显式接受"无验证"。

🟠 P1 — 真实缺陷

P1已修 ✓单例状态竞态:BUILD 中开新需求

模块级 let wf 单例,BUILD 跑到一半 /wf new 会切换引用导致写错对象。

改进:BUILD 中拒绝 /wf new(单例锁)。

P1已修 ✓extractJson 容错解析是"猜"

用 indexOf('{')/lastIndexOf('}') 可能解析出语法合法但语义错误的 JSON,静默生成缺失子任务规格。

改进:JSON 解析失败或缺必要字段时严格校验、响亮报错(修了 KNOWN_ISSUES P1 #3)。

P1已解决 ✓aggregateMetrics 靠字段名猜测(随 reasonix 移除 obsolete)

原问题:key.includes("cost") 这类启发式匹配过去对上 reasonix v1.11 字段名,换字段名会静默算成 undefined。

现状:reasonix 已迁移为 omp dev subagent,不再产出 reasonix -metrics JSON,这段聚合已 obsolete;需随 omp message_end hook 重写或移除。

P1未修review.md 无强制力

review 是建议性(设计决定不改),但 BUILD 完成的 notify 和普通 info 视觉无区别,即使有 blocker 也没有更强提示。

建议:review 出现"blocker"时 notify 升级为 error,并在 state.json 记录 reviewSeverity。

⚪ P2 — 未验证的合理风险

P2跨平台:全程只在 macOS 验证

runVerify 用 bash -lc,Windows 无 bash 会直接失效;路径分隔符、符号链接行为未验证。

P2waitTurnComplete 的 2.5s 静默期是经验值

600s 硬顶;网络抖动/模型输出忽快忽慢可能误判 turn 已结束(提前截断)。真实边界场景从未验证。

P2slug() 硬切可能切在多字节字符中间

.slice(0, 40) 按 UTF-16 code unit 切,非常规 Unicode 标题可能生成非法文件名。

P2测试只覆盖状态机逻辑,不覆盖真实故障

test/build.test.ts 全用 fake-omp 桩(原 execReasonix),没测:网络断/限流/omp --print 输出异常、长时间超时、10+ 子任务撞 token 上限。

P2产品定位:小需求过度工程,大需求验证不足

极简需求走完整链路成本远超直接用 omp;真正需要的复杂需求从未被真实测试覆盖(都是玩具级冒烟)。

⚠️ 当前架构的固有限制(非 bug,设计取舍)

并行模型:maxParallel 是并行 dev 上限

独立 task 并行派发给不同 omp dev subagent(取代旧的依赖链同 dev --continue 路由)。maxParallel=3 是经理可并行的 dev 数。经理是驻留 LLM,默认 stage 级委派,异常时细粒度介入。

调度可靠性依赖经理 LLM 的判断

拆分/分配策略的正确性取决于经理(deepseek-pro)的理解,而非确定性代码。复杂依赖图下可能拆分不当或分配次序欠优。
